# Deployment layout v1

This page is the directory layout `keystonectl` requires around a keystone-mcp
process. The tool does not install keystone-mcp and does not care whether the
process arrived from a published compose file, from another product's setup, or
later from Helm. It only needs this directory.

Why: [ADR 0006](../adr/0006-keystonectl-is-a-separate-product.md).

`layout_version` in `services.lock.yaml` is `1`. There is no migration to
another layout in this release.

## Files and owners

Paths are relative to the deployment root.

| Path | Owner | What keystonectl does |
|---|---|---|
| `docker-compose.yml`, or the first of `docker-compose.yaml`, `compose.yaml`, `compose.yml` | operator | reads it (`init`, `check`) |
| `docker-compose.packages.yml` | keystonectl | rewrites the whole file when the layout or the installed set changes |
| `packages/` (mode 755) | keystonectl | creates the directory |
| `packages/<name>.yml` | keystonectl when `managed` is `generated`; the operator when `ejected` | rewrites the whole file, and compares `fragment_sha256` from the lock before doing so |
| `packages/<name>.override.yml` | operator | never writes it; the packages compose file includes it when it exists |
| `packages/<name>.env`, `packages/<name>.mcp.env`, `packages/<name>.<kind>.env` (mode 600) | keystonectl | rewrites the whole file. The first reaches every container of the package, the second only the MCP facade, the third only the containers named for that resource |
| `keystonectl/` (mode 755) | keystonectl | creates the directory and mounts it into keystone-mcp |
| `keystonectl/upstreams.yaml` (mode 644) | shared | changes only registry entries whose `name` is in the lock, and keeps every other entry in its previous order |
| `keystonectl/catalog-snapshot.yaml` (mode 644) | shared | changes only `<namespace>_*` names in `active` for namespaces this install owns |
| `policy/rbac-policy.yaml`, or the file named by `KEYSTONE_MCP_RBAC_POLICY_PATH` | operator and the policy tools | reads it (`check`) |
| `.env` (mode 600) | operator | writes only inside the managed block below |
| `services.lock.yaml`, and its `.bak` and `.lck` siblings (mode 600) | keystonectl | the install state. `.lck` is held for the whole state-changing command |
| `sources.yaml` (mode 600) | keystonectl (`catalog add`); the operator may edit it | format is in [Catalog sources](catalog.md#sources). `init` does not create it |
| `.keystonectl/` (mode 700) | keystonectl | catalog and package cache, `secrets/` (mode 700), and `tmp/`. Contains a `.gitignore` whose only line is `*` |
| `.keystonectl/tmp/` (mode 700) | keystonectl | clones are built here and renamed into place on the same file system |
| `.gitignore` | operator | created only when the file is absent, with the lines below |

```
/services.lock.yaml*
/packages/*.env
/.keystonectl/
/.env
/sources.yaml
```

keystonectl never modifies an operator file, and never modifies a registry or
snapshot entry it does not own.

Why: [ADR 0005](../adr/0005-operator-freedom-override-eject-adopt.md).

## How files are written

A write goes to a temporary file in the same directory, then `fsync`, then
`rename`. Modes are the ones in the table above.

Before rewriting a shared file (`keystonectl/upstreams.yaml`,
`keystonectl/catalog-snapshot.yaml`, or `.env`), copy the current bytes to
`<file>.bak`. Those files are not secret: keystone-mcp reads the registry and
the snapshot as uid 10001, so they stay mode 644. Rewriting them drops comments.
The first time a file that contains comments is rewritten, copy it once to
`<file>.orig` and report the warning `comments_dropped`. Later rewrites do not
refresh `.orig`.

`init` creates missing files and does not rewrite a file that is already
present, except `services.lock.yaml` when recognition produced a different
`layout`, and `docker-compose.packages.yml` when the rendered bytes differ.
The installer adds the backup and the comment warning when it rewrites the
shared files during install.

## The packages compose file

The deployment is always started as:

```
docker compose --project-directory <root> -f <operator compose> -f docker-compose.packages.yml [--profile <p> ...] up -d
```

The file list and the profiles come from `layout.compose_files` and
`layout.profiles`. `docker-compose.packages.yml` is an override on top of the
operator's compose file. Compose merges the keystone-mcp service from both
files. The operator's compose file is not edited.

`include` with a list under `path` needs Docker Compose 2.24 or newer. `check`
and `apply` verify `docker compose version --short` and refuse with
`compose_too_old` when it is older. `init` does not call Docker.

The file looks like this once packages are installed:

```yaml
# Generated by keystonectl. Do not edit: this file is rewritten on every change.
# Use: docker compose -f docker-compose.yml -f docker-compose.packages.yml up -d
# Change a package in packages/<name>.override.yml instead.
include:
  - path: [packages/file-mcp.yml, packages/file-mcp.override.yml]
services:
  keystone:
    environment:
      KEYSTONE_MCP_UPSTREAMS_PATH: /etc/keystone-mcp/keystonectl/upstreams.yaml
      KEYSTONE_MCP_RBAC_CATALOG_SNAPSHOT: /etc/keystone-mcp/keystonectl/catalog-snapshot.yaml
    volumes:
      - ./keystonectl:/etc/keystone-mcp/keystonectl:ro
    networks: [keystone-mcp-upstreams]
networks:
  keystone-mcp-upstreams:
    name: keystone-mcp-upstreams
    external: true
```

Before a keystone-mcp service has been recognized, the file is only the three
comment lines and an external `keystone-mcp-upstreams` network. There is no
`services` key yet.

`include` is omitted when nothing is installed. One entry is written per
package, sorted by name. The override path is added to that `path` list only
when `packages/<name>.override.yml` exists. `render_packages_compose` in this
release writes the service extension and, when package names are passed, the
`include` entries for `packages/<name>.yml`. The installer adds the override
path.

Inside a file pulled in by `include`, a relative path is resolved from the
directory that contains that file (`packages/`). A fragment refers to
`file-mcp.env`, not to `packages/file-mcp.env`.

The keystone-mcp service extension is written from the first `init` that finds
the service. Without it, keystone-mcp does not see the registry, the snapshot,
or the service network. The service name is `layout.keystone_service`.

The service network is always the external Docker network
`keystone-mcp-upstreams`. The installer creates it when it is missing. If the
operator's service is already attached to a network whose `name` is
`keystone-mcp-upstreams`, the packages file does not declare that network
(`attached_by: operator`). Compose will not accept a second key for the same
network. Match the network by the `name` field in the top-level `networks`
mapping, not by the key: a key such as `keystone_upstreams` can still carry
`name: keystone-mcp-upstreams`. When the operator's service declares no
`networks`, the override lists `[default, keystone-mcp-upstreams]` so the
implicit project network is kept. That choice is stored as
`layout.upstreams_network.include_default_network: true`. When the flag is
absent it is false.

A single-file bind mount keeps the inode. After an atomic replace on the host,
the container would keep reading the old registry. The registry and the snapshot
therefore live in `<root>/keystonectl/` and are mounted as that directory at
`/etc/keystone-mcp/keystonectl/` (read-only). The mount does not touch anything
the operator already mounted under `/etc/keystone-mcp/`. keystone-mcp reads the
registry only at process start until a later release reloads it on `SIGHUP`.
After writing the registry, the installer restarts the keystone-mcp service.

An `environment` entry in this override wins over the same name in `env_file`
and over the same name in the operator's `environment`, because this file is
the last `-f`.

`environment` in the operator's compose file may be a mapping (`KEY: value`)
or a list (`- KEY=VALUE`, or a bare `- KEY` that passes a value through from
the project environment). `env_file` may be a string, a list of strings, or a
list of `{path, required}` objects. The first entry is the one recorded in
`layout.env_file`.

## The managed block in `.env`

```
# >>> keystonectl: managed block, do not edit >>>
KEYSTONE_MCP_UPSTREAM_FILES_BEARER=…
KEYSTONE_MCP_UPSTREAM_FILES_IDENTITY_SECRET=…
# <<< keystonectl <<<
```

Only lines matching `^KEYSTONE_MCP_UPSTREAM_[A-Z0-9_]+=` appear inside the
block. The block is appended at the end when it is missing. Lines outside the
block are left byte for byte. If the operator already sets one of those names
outside the block, the write is refused with `env_name_conflict`. A name
without the prefix is a programming error (`ValueError`).
`replace_managed_env_block` returns the new text. The installer writes the
values; `init` does not.

## init

`keystonectl init <root>` creates what is missing and does not overwrite what
is already there.

- The root may be missing, empty, or already contain `services.lock.yaml`.
  The files created when absent are `packages/`, `docker-compose.packages.yml`,
  `keystonectl/upstreams.yaml` (`schema_version: 1`, `entries: []`),
  `keystonectl/catalog-snapshot.yaml` (`active: []`), `services.lock.yaml`,
  `.keystonectl/` (with `secrets/`, `tmp/`, and `.gitignore`), and `.gitignore`
  when that file is absent. `sources.yaml` is not created; without it the
  default catalog is used.
- When a compose file that runs keystone-mcp is present, recognition runs and
  `layout` is stored in the lock. When it is not, `layout` is null, the result
  is not ready, and the warning is `keystone_compose_missing`: put
  keystone-mcp's `docker-compose.yml` and `.env` here (see keystone-mcp
  `examples/production`) and run `keystonectl init` again.
- A compose file without a lock is refused with `adopt_required`: this
  directory already runs a compose project; use `--adopt`.
- Any other non-empty directory without a compose file and without a lock is
  refused with `root_not_empty`.
- Running `init` again on a finished root writes nothing. If recognition
  produced a different `layout` because the operator changed the compose file,
  the lock's `layout` is updated and the warning `layout_changed` lists the
  field names.

`layout.keystone_mcp_version` is the operator's answer when the image does not
say which release is running. `init` stores null. On a later `init`, a version
already stored in the lock is kept when `keystone_image` and `keystone_build`
are unchanged, so the answer is not wiped. If either of those two fields
changed, the stored version is cleared.

`plan_init` does not write. `apply_init` writes only the paths in the plan and
returns those relative paths. The initial lock is written here. Locking,
backup, and atomic replace during later installs belong to the installer.

## init --adopt

`keystonectl init --adopt <root>` recognizes a directory that already runs
compose. Compose is read with YAML, not with Docker. `${VAR}`, `${VAR:-default}`,
`${VAR-default}`, `${VAR:?message}`, `${VAR?message}`, `${VAR:+}`, `${VAR+}`,
a bare `$VAR`, and `$$` are substituted before the YAML parse. Values come from
`<root>/.env`, and a name also passed in the caller's `environ` argument wins.
These functions do not read the process environment themselves; the installer
passes the environment it wants used. An unset variable becomes an empty
string and produces the warning `compose_variable_unset: NAME`. An empty value
uses the `:-` and `:?` defaults the same way Compose does. `$$` becomes a
single `$`.

1. The compose file is the first name in `docker-compose.yml`,
   `docker-compose.yaml`, `compose.yaml`, `compose.yml`. None of them is
   `compose_not_found`. A file that is not a YAML mapping is
   `compose_unparseable`.
2. The keystone-mcp service is `--keystone-service` when that argument is set.
   Otherwise it is every service whose image repository's last segment is
   `keystone-mcp` (for example `ghcr.io/keystone-codes/keystone-mcp:0.5.0` or
   `keystone-mcp:local`). If no image matches, a service named `keystone-mcp`
   is used. None is `keystone_service_not_found`. Two or more is
   `keystone_service_ambiguous`, with `choices` set to the service names.
3. The lock records the image, `build.context` when present, the service's
   profiles, and the project name (`name:` at the top of the file, otherwise
   the directory name in lower case with only `[a-z0-9_-]` kept). `flavor` is
   `keystone-mcp-example` when the service is `keystone` and the project is
   `keystone-production`, `keystone-deploy` when the service is `keystone-mcp`
   with profile `keystone-mcp` and it is already on `keystone-mcp-upstreams`,
   and `custom` otherwise. Flavor is a hint. It does not change behavior.
4. The env file is the first `env_file` of the service, and it must stay
   inside the root. No `env_file` is `keystone_env_file_missing`.
5. Service `environment` overrides `env_file`. A container path is mapped to
   the host through the service's bind mounts. Short form `SRC:DST[:mode]`
   counts when `SRC` starts with `.`, `/`, or `~`. Long form counts when
   `type` is `bind`. The mount whose target equals the path, or is a parent of
   it, wins; the longest target wins. A result outside the root is
   `path_outside_root`. A path that is not mounted is `registry_path_unmapped`.
   The same two codes are used for the policy file and the snapshot; the
   message names the setting.
6. keystone-mcp reads `<root>/keystonectl/upstreams.yaml` through the packages
   compose file. On the first adopt, that file is filled from the operator's
   registry and the operator's file is not modified. The operator's registry
   is the file named by `KEYSTONE_MCP_UPSTREAMS_PATH` when that variable is
   set, otherwise `<root>/upstreams.yaml` when that file exists. It must be
   `schema_version: 1` with an `entries` list, or the result is
   `registry_invalid`. Entries are copied once, in the same order, and only
   when `keystonectl/upstreams.yaml` does not exist yet. If there were entries,
   the warning is `registry_moved`. If there is neither a path nor a file, and
   `KEYSTONE_MCP_UPSTREAMS` is a non-empty JSON array, the result is
   `registry_inline`: move these entries to `upstreams.yaml` and set
   `KEYSTONE_MCP_UPSTREAMS_PATH`; keystonectl does not edit inline JSON. An
   empty string is an empty registry. `[]` is an empty registry plus the
   warning `inline_registry_ignored`.
7. `KEYSTONE_MCP_RBAC_CATALOG_SNAPSHOT` is mapped the same way. Its `active`,
   `reserved`, and `wip` lists are copied once into
   `keystonectl/catalog-snapshot.yaml` when that file does not exist yet, with
   the warning `snapshot_moved`. When the variable is unset, an empty snapshot
   (`active: []`) is created.
8. `KEYSTONE_MCP_RBAC_POLICY_PATH` is mapped the same way. When it is unset,
   `policy` is null and the warning is `policy_not_configured`. `check` then
   skips the policy comparison. A deployment does not have to ship a policy.
9. When the service is already on a network named `keystone-mcp-upstreams`,
   `attached_by` is `operator`. Otherwise it is `keystonectl`, and `default`
   is included when the service declares no networks.
10. Missing keystonectl files are created, and `docker-compose.packages.yml`
    and the lock are written. The operator's compose file, `.env`, policy,
    registry, and snapshot are not modified.
11. The result includes `InitPlan.compose_command`, the two-file command
    above. The installer prints it as the last line of text output and as
    `result.compose_command`. Without the second `-f`, keystone-mcp does not
    see the registry.

### Refusals

| Code | Exit | When | What to do |
|---|---|---|---|
| `keystone_service_ambiguous` | 2 | more than one service runs keystone-mcp | pass `--keystone-service NAME`; `choices` lists the names |
| `adopt_required` | 3 | `init` found a compose file and no lock | run `init --adopt` |
| `root_not_empty` | 3 | the directory has other files, and no compose file and no lock | use an empty directory, or `--adopt` when compose is already there |
| `compose_not_found` | 3 | `--adopt` found none of the compose file names | put the compose file in the directory |
| `compose_unparseable` | 3 | the compose file is not a YAML mapping | fix the file; recognition does not call Docker |
| `keystone_service_not_found` | 3 | no service runs keystone-mcp | pass `--keystone-service NAME` if the service was renamed |
| `keystone_env_file_missing` | 3 | the keystone-mcp service has no `env_file` | add `env_file: .env` |
| `path_outside_root` | 3 | a mapped path leaves the deployment directory | mount a path inside the directory |
| `registry_path_unmapped` | 3 | the registry, policy, or snapshot path is not a bind mount | add a bind mount of the path or of a parent directory |
| `registry_invalid` | 3 | the registry is not `schema_version: 1` with an `entries` list, or `KEYSTONE_MCP_UPSTREAMS` is not a JSON array | fix the file, or use `[]` |
| `registry_inline` | 3 | `KEYSTONE_MCP_UPSTREAMS` is a non-empty JSON array and there is no registry file | move the entries into `upstreams.yaml` and set `KEYSTONE_MCP_UPSTREAMS_PATH` |
| `env_name_conflict` | 3 | a managed name is already set outside the block | remove that line, or rename it |

Exit 2 is the question the installer reports as
`missing: {var: "--keystone-service", kind: "argument", choices: [...]}`.
Every other refusal is exit 3 and is not retryable. `LayoutError.choices` is
set only for `keystone_service_ambiguous`.

### Warnings

`keystone_compose_missing`, `layout_changed`, `compose_variable_unset`,
`inline_registry_ignored`, `registry_moved`, `snapshot_moved`,
`policy_not_configured`, `comments_dropped`. A warning does not change the
exit code.

## services.lock.yaml

The only lock schema in this release is `src/keystonectl/schemas/lock-v1.json`
(JSON Schema draft 2020-12). A full example is
`docs/spec/examples/services.lock.yaml`. `lock_errors` checks the schema and
the rules below and returns a list of messages; an empty list means the
document is valid.

`additionalProperties` is false on every object, so a secret value has nowhere
to sit. The lock stores names of variables, paths, image references, and
non-secret answers. Hashes are `^[0-9a-f]{64}$`, commits are `^[0-9a-f]{40}$`,
and timestamps are UTC ISO 8601 with a `Z` and no fractional seconds.

`layout_version` must be `1`. Anything else is reported as
`layout_version: this keystonectl supports layout 1`.

`services[]` and `resources[]` are lists. `services[].name` is unique.
`role` is `service` or `resource`. A resource has null `registry_name`,
`namespace`, and `url`, and its `managed` value is not `remote`.

`managed: generated` requires `package`, `version`, `ref`, `commit`,
`manifest_sha256`, `containers`, `fragment`, and `fragment_sha256`.
`ejected` requires the same fields, and `fragment_sha256` may be null.
`remote` forbids `package`, `version`, `ref`, `commit`, `containers`, and
`fragment*`, requires `registry_name`, `namespace`, and `url`, and may set
`filters` (`tool_prefix`, `include_prefixes`, `exclude_prefixes`,
`strip_prefix`). Every other service has `filters: null`.

`containers.<role>` is `{service, image, init}` and `service` equals
`<package>-<role>`. `registry_name`, `namespace`, and `url` are a string or
null. When `registry_name` is null, `tools` is empty and `env.keystone` is
empty. `env.files` contains only `packages/<name>.env`,
`packages/<name>.mcp.env`, and `packages/<name>.<kind>.env`.

`public.state` is `none`, `pending`, or `ready`. `ready` requires `domain`,
`tls` (`keep`, `certbot`, `custom`, or `manual`), and `host_port` in
47600–47699. The other `public` fields are the ones in the example.
`dns` is `checked` or `skipped`. `disabled_sites` lists the nginx sites a
successful takeover disabled, by file name. A failed apply removes the names
it disabled in that run and enables those sites again. `service remove`
restores every name still in the list.
`took_over` is the single-site field written before `disabled_sites`
existed; a lock that still has it and no `disabled_sites` is valid, and
keystonectl treats it as a one-item list.

`resources[].kind` is unique and is `s3` or `postgres` (one provider per kind).
`s3` params are `endpoint`, `region`, and `path_style`. `postgres` params are
`host`, `port`, and `sslmode`. An `s3` consumer has `service`, `bucket`, and
`provisioned_at`. A `postgres` consumer has `service`, `database`, `user`,
`extensions`, and `provisioned_at`. `origin: external` has `provider: null`.
`origin: catalog` names a `services[]` entry whose `role` is `resource`.

Every kind in `services[].resources` exists in `resources[]`. Every
`consumers[].service` and every catalog `provider` exists in `services[]`.
Otherwise the message is `<path>: unknown resource '<name>'` or
`<path>: unknown service '<name>'`.

## Known layouts

**keystone-mcp `examples/production/`.** Project `keystone-production`, service
`keystone`, image `ghcr.io/keystone-codes/keystone-mcp` with a pinned tag,
`env_file: .env`, network `keystone`, and bind mounts of `./policy` and
`./upstreams.yaml`. There is no catalog snapshot in the published directory.
`init --adopt` records flavor `keystone-mcp-example`, attaches
`keystone-mcp-upstreams` from the packages file (`attached_by: keystonectl`),
and leaves the operator's compose file, `.env`, policy, and `upstreams.yaml`
unchanged. The registry keystone-mcp will read is `keystonectl/upstreams.yaml`.

**keystone-deploy `mcp/`.** Service `keystone-mcp` with profile `keystone-mcp`,
the pinned image `ghcr.io/keystone-codes/keystone-mcp:0.5.0@sha256:…` (a local
source build is a separate `docker-compose.local.yml`, started with
`./start.sh --local`), and networks `mcp_net`, `keystone_upstreams`, and a
third, internal-only network private to this file. The top-level key
`keystone_upstreams` has `name: keystone-mcp-upstreams`, so `attached_by` is
`operator` and the packages file does not declare that network. The published
`.env.example` does not set `KEYSTONE_MCP_UPSTREAMS` — the install script
strips that key from `mcp/.env` on every write — and there is no registry file
and no policy file, so adopt warns `inline_registry_ignored` and
`policy_not_configured` and writes an empty registry. The same recognition
works before and after that directory grows a real `upstreams.yaml`.

## Layout versions

This release reads and writes `layout_version: 1` only. A lock with any other
value is rejected. No layout migration is performed.

## Helm later

A later release can add a second generator that emits Helm values from this
same directory layout and the same `services.lock.yaml`.
